POLÍTICA OBLIGATORIA DE TESTS (REGLA CRÍTICA)
=====================================================================

TESTS OBLIGATORIOS: - Cada vez que: - se implemente una funcionalidad
nueva - se modifique lógica existente - se arregle un bug - se
refactorice código ChatGPT DEBE generar SIEMPRE un prompt adicional para
crear o actualizar tests.

REGLAS: - Ninguna funcionalidad se considera finalizada sin test
asociado. - Si ya existen tests relacionados: - deben ampliarse o
actualizarse. - Si no existen: - crear test mínimo de regresión.

OBJETIVO: - Evitar romper funcionalidades anteriores sin detectarlo. -
Detectar regresiones inmediatamente tras cada sprint.

FLUJO OBLIGATORIO DE PROMPTS: 1) Prompt implementación funcionalidad 2)
Prompt creación/actualización de tests 3) Prompt ejecución/verificación
de tests

REGLA CRÍTICA: - Si ChatGPT detecta que se ha avanzado sin tests en
funcionalidades recientes, debe PRIORITIZAR crear tests antes de
continuar desarrollando nuevas features.

FILOSOFÍA: - Mejor tests simples que ausencia total de tests. - Tests
pequeños y frecuentes > tests grandes tardíos.

===================================================================== 🔒
TEST GATE (OBLIGATORIO ANTES DE AVANZAR) — NIVEL SENIOR
=====================================================================

REGLA ABSOLUTA: - ChatGPT NO puede proponer nuevas funcionalidades si: -
la última funcionalidad implementada NO tiene test asociado - o los
tests existentes no cubren el cambio realizado.

VALIDACIÓN PRE-SPRINT: Antes de generar prompts de un nuevo sprint,
ChatGPT debe comprobar:

1)  ¿La última funcionalidad tiene test?
2)  ¿El último bugfix tiene test de regresión?
3)  ¿Se han actualizado tests afectados por refactor?

Si alguna respuesta es NO: - PRIORIDAD AUTOMÁTICA → generar prompts SOLO
de tests. - Bloquear avance funcional hasta que existan.

EXCEPCIÓN: - Solo se permite continuar sin tests si el proyecto NO tiene
aún infraestructura de testing. - En ese caso, el siguiente sprint DEBE
crear la base de testing.

SECUENCIA OBLIGATORIA POR SPRINT: 1) Implementación o fix 2) Tests
obligatorios 3) Verificación tests 4) Commit limpio

INDICADORES DE RIESGO: ChatGPT debe asumir que existe alto riesgo si: -
Se modifican modelos de datos - Se toca parsing/importación - Se cambia
lógica core - Se refactorizan rutas críticas

En estos casos: - Añadir SIEMPRE test de regresión específico.

REGLA FINAL: NINGÚN SPRINT SE CONSIDERA COMPLETO SI NO EXISTE AL MENOS
UN TEST NUEVO O ACTUALIZADO.

V9 — CHANGELOG ENGINE (HISTORIA CLARA DE CAMBIOS)
=====================================================================

OBJETIVO: Evitar confusión por cambios de lógica y eliminar “bugs
fantasma” causados por olvidar cómo funcionaba antes el sistema.

NUEVO ARCHIVO OBLIGATORIO DEL PROYECTO:

7)  changelog.md

-   Registro breve y claro de cambios relevantes.
-   Enfocado en comportamiento, no en detalles técnicos.
-   Sirve para entender rápidamente qué cambió y por qué.

CUÁNDO ACTUALIZAR changelog.md (OBLIGATORIO): Cada vez que ocurra alguno
de estos casos:

-   Nueva funcionalidad (FEATURE)
-   Bugfix que cambia comportamiento (FIX con impacto)
-   Cambio de flujo o lógica existente
-   Refactor que pueda afectar resultados
-   Cambios en modelos de datos o parsing/importación

FORMATO OBLIGATORIO DE ENTRADA:

YYYY-MM-DD — : 

ANTES: - <1 línea>

AHORA: - <1 línea>

IMPACTO: - <1 línea>

REGLAS: - Máximo 3–6 líneas por entrada. - Lenguaje simple. - Sin
términos técnicos complejos. - Si un cambio invalida una suposición
anterior, debe registrarse aquí.

INTEGRACIÓN CON WIKIS: - Si el changelog indica cambio de flujo: -
actualizar wiki_tecnica.md (reescritura si aplica) - actualizar
wiki_usuario.md si afecta al uso

REGLA FINAL: - Si el usuario reporta un “error raro” tras varios
sprints, ChatGPT debe revisar primero el changelog para detectar si es
un cambio esperado y no un bug real.
